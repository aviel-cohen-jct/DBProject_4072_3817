## 1. סקירה

בשלב ה' הפכנו את ממשק ה-React של "ספורטקס" (בורסת שחקני הכדורגל) לאפליקציה מלאה שעובדת מול בסיס הנתונים המשולב של הפרויקט: 7 הטבלאות של הבורסה, 15 הטבלאות של מערכת הליגה האמיתית שהתקבלה בשלב ג', טבלת הגישור `PLAYER_MAPPING`, שני ה-Views, ושתי הפונקציות, שתי הפרוצדורות ושני הטריגרים משלב ד'.

עיקרון מנחה: **אפליקציה אמיתית, לא "עורך טבלאות".** ההוראות מאפשרות ש-CRUD יתבצע "בעקיפין, לפי אופי האפליקציה", ולכן כל טבלה מקבלת הקשר עסקי: הסוחר פועל דרך מסכי מסחר, ומנהל הליגה מנהל מחזורים, שחקנים, קבוצות, משחקים וסטטיסטיקות במסכי back-office. אף מסך לא מציג מזהים של מפתחות זרים; תמיד מוצג השם שאליו המפתח מצביע.

המערכת מחולקת לשני תפקידים שנבחרים במסך הכניסה:

| תפקיד | מה הוא עושה | טבלאות |
|---|---|---|
| **סוחר** | קונה ומוכר שחקנים, מנהל את הסגל והחשבון, צופה בתובנות שוק | USERS, PLAYERS, USER_SQUADS, TRANSACTIONS, PRICE_HISTORY (+ View) |
| **מנהל ליגה** | CRUD מלא על כל 22 הטבלאות, סגירת מחזור ועדכון מחירים | כל הטבלאות |

## 2. כלים ודרך העבודה

| שכבה | טכנולוגיה | למה |
|---|---|---|
| Frontend | React 19, TypeScript, Vite 8, Tailwind CSS | המשך ישיר של המסכים משלב א' (אותה ערכת עיצוב, אותם 4 מסכי מסחר) |
| Backend | Node.js, Express 4, `pg` (node-postgres) | שרת API דק שמתרגם בקשות HTTP ל-SQL פרמטרי |
| בסיס נתונים | PostgreSQL 18 ב-Docker (`PostgreSQL_DB`) | אותו מסד מכל השלבים הקודמים, משוחזר מ-`backup4.sql` |
| בדיקות | דפדפן + `agent-browser` (Chrome headless) | הרצה אמיתית של כל זרימה וצילומי המסך בדוח |

**דרך העבודה:**

1. **מיפוי הסכמה.** שלפנו מ-`information_schema` את כל העמודות, המפתחות הראשיים, המפתחות הזרים ואילוצי ה-CHECK של 22 הטבלאות. מהם נבנה קובץ מטא-דאטה אחד (`server/meta.js`).
2. **שרת גנרי.** במקום לכתוב 22×4 endpoints, כתבנו Router אחד שמקבל שם טבלה ובונה את ה-SQL מהמטא-דאטה: `SELECT` עם `LEFT JOIN` לכל מפתח זר (כדי להחזיר שם במקום מזהה), `INSERT` עם הקצאת מזהה אוטומטית, `UPDATE`/`DELETE` לפי מפתח (כולל מפתחות מורכבים), ורשימת אפשרויות לבחירה לפי שם.
3. **רכיב ממשק גנרי.** רכיב `EntityPanel` מציג כל טבלה: טבלה עם חיפוש ודפדוף, כפתורי הוספה / עדכון לפי מפתח / מחיקה לפי מפתח, וטופס שנבנה אוטומטית לפי סוגי השדות (טקסט, מספר, תאריך, רשימת ערכים, בחירת מפתח זר עם חיפוש).
4. **מסכים עסקיים.** על הבסיס הגנרי נבנו מסכי המנהל (master-detail: משחק → קבוצות, אצטדיון, שופטים, סטטיסטיקות) ומסכי הסוחר, שקוראים לפרוצדורות ולפונקציות של שלב ד'.
5. **בדיקה מקצה לקצה.** כל זרימה הורצה מול ה-DB האמיתי: קנייה שמתקבלת, קנייה שנדחית ע"י הטריגר, עדכון מחיר שיוצר היסטוריה, סגירת מחזור, הוספה ומחיקה בכל סוג טבלה (מפתח פשוט, מפתח מורכב, מפתח שהוא גם מפתח זר).

## 3. ארכיטקטורה

```
דפדפן (React, http://localhost:5173)
   │  fetch /api/...  (Vite proxy)
   ▼
Express (server/index.js, פורט 5001)
   ├── /api/meta                 מטא-דאטה של 22 הטבלאות         (server/meta.js)
   ├── /api/tables/:table        CRUD גנרי + חיפוש + אפשרויות FK  (server/crud.js)
   ├── /api/queries/:id          8 שאילתות שלב ב' עם פרמטרים      (server/reports.js)
   ├── /api/programs/*           fn_/prc_ של שלב ד'               (server/reports.js)
   └── /api/players, /api/users… ה-endpoints המקוריים משלב א'
   │  SQL פרמטרי (pg.Pool)
   ▼
PostgreSQL – fantasy_db (22 טבלאות, 2 Views, 2 פונקציות, 2 פרוצדורות, 2 טריגרים)
```

### 3.1 המטא-דאטה (`server/meta.js`)

לכל טבלה מוגדרים: שם בעברית, עמודות המפתח, האם המזהה מוקצה אוטומטית, ביטוי SQL ל"שם התצוגה" של רשומה (משמש כשטבלה אחרת מצביעה עליה), ורשימת העמודות עם סוג, תווית, ערכי enum, מפתח זר ורמז למשתמש. דוגמה:

```js
transactions: {
  label: 'עסקאות', pk: ['transaction_id'], autoPk: true, orderDesc: true,
  cols: [
    c('transaction_time', 'זמן', 'timestamp', { required: true }),
    c('user_id',   'משתמש', 'int', { fk: 'users',   required: true }),
    c('player_id', 'שחקן',  'int', { fk: 'players', required: true }),
    c('action_type', 'סוג פעולה', 'enum', { values: ['BUY', 'SELL'] }),
    c('transaction_price', 'מחיר', 'int', { hint: 'נבדק ע"י טריגר: תקציב בקנייה, בעלות במכירה' }),
  ],
},
```

שמות טבלאות ועמודות מגיעים **תמיד** מהמטא-דאטה ולא מהבקשה (whitelist), וכל הערכים עוברים כפרמטרים. כך אין SQL Injection.

### 3.2 הצגת שמות במקום מזהים

לכל עמודת מפתח זר השרת מוסיף `LEFT JOIN` לטבלת היעד ומחזיר עמודה נוספת `<col>__label` עם ביטוי התצוגה שלה. למשל בטבלת `MATCHTEAM` העמודה `matchid` מוצגת כ-"Argentina FC 93 - Austria FC 44 (14/08/2023)" (שמות הקבוצות מ-`MATCHTEAM`+`TEAM` ותאריך המשחק), ו-`teamid` מוצג כשם הקבוצה. בטפסים, שדה מפתח זר הוא תיבת חיפוש שמציעה שמות, והמזהה נשמר מאחורי הקלעים.

### 3.3 זרימת עדכון לפי מפתח

בהתאם להוראות: המשתמש מזין רק את המפתח (או המפתח המורכב) → לחיצה על "טען רשומה" → השרת מחזיר את הרשומה → הטופס מתמלא, שדות המפתח ננעלים → המשתמש עורך ושומר. אותה זרימה משמשת גם למחיקה (הרשומה מוצגת לקריאה בלבד עם אישור).

### 3.4 שגיאות בסיס הנתונים

שגיאות PostgreSQL מתורגמות להודעות ידידותיות: מפתח כפול, הפרת מפתח זר במחיקה ("קיימות רשומות מקושרות"), הפרת CHECK, שדה חובה חסר, וחריגות `RAISE EXCEPTION` של הטריגרים שלנו מוצגות כפי שהן (כבר בעברית). הודעות `RAISE NOTICE` של `prc_execute_trade` נתפסות בשרת ומוצגות למשתמש, כך שרואים אם הטריגר דחה את העסקה.

## 4. מסכי המערכת

### 4.1 מסך כניסה
בחירת סוחר מרשימת המשתמשים (`USERS`) וכניסה, הרשמה של משתמש חדש (INSERT ל-`USERS` עם תקציב התחלתי), או כניסה כמנהל ליגה.

### 4.2 צד הסוחר
| מסך | תיאור | DB |
|---|---|---|
| **שוק השחקנים** | מחירון כל השחקנים עם חיפוש וסינון לפי עמדה, שינוי 24 שעות | `PLAYERS`, `PRICE_HISTORY` |
| **פרופיל שחקן** | גרף היסטוריית מחיר, נתוני שוק, כרטיס "ביצועים בעולם האמיתי" (משחקים, שערים, בישולים, טאקלים) מה-View `V_BURSA_PLAYER_SCOUTING` דרך `PLAYER_MAPPING`, וכפתורי **קנייה / מכירה** שמפעילים את הפרוצדורה `prc_execute_trade` | `prc_execute_trade`, טריגר `trg_transactions_validate` |
| **הסגל שלי** | כרטיסי שווי ורווח, כרטיס "הערכת שווי רשמית" מהפונקציה `fn_calculate_portfolio_value` (שגם מעדכנת `Portfolio_Yield`), העלאה להרכב / הורדה לספסל (UPDATE `USER_SQUADS`) | `USER_SQUADS`, `fn_calculate_portfolio_value` |
| **היסטוריית פעולות** | ציר זמן של כל העסקאות, נשלף דרך ה-REF CURSOR של `fn_get_user_transactions` | `fn_get_user_transactions` |
| **תובנות שוק** | 8 השאילתות של שלב ב' ככרטיסי דוח בשמות טבעיים, עם פילטרים במקום ערכים קשיחים (תאריך, שם קבוצה) | שאילתות שלב ב' |
| **החשבון שלי** | עריכת שם המשתמש, מצב החשבון מהפונקציה, מחיקת חשבון (נחסמת ע"י מפתח זר אם יש עסקאות) | `USERS` |

### 4.3 צד מנהל הליגה
| מסך | טבלה ראשית | פירוט (master-detail) | פעולה מיוחדת |
|---|---|---|---|
| **מחזורים** | `ROUNDS` | – | **סגירת מחזור ועדכון מחירים**: מריץ `prc_process_round_price_update`, מציג את הודעות הפרוצדורה ואת רשומות `PRICE_HISTORY` שהטריגר `trg_players_price_history` יצר |
| **שחקני בורסה** | `PLAYERS` | `PLAYER_MAPPING` (קישור לשחקן אמיתי), `PRICE_HISTORY` | שינוי מחיר יוצר רשומת היסטוריה אוטומטית |
| **משתמשים** | `USERS` | `USER_SQUADS`, `TRANSACTIONS` | הוספת עסקה נבדקת ע"י הטריגר |
| **יומן עסקאות** | `TRANSACTIONS` | – | |
| **קבוצות ואצטדיונים** | `TEAM` | `COACHEDBY`, `PLAYSFOR_PLAYER`, `PLAYSFOR_GK`; וכן `STADIUM` | |
| **שחקנים ושוערים** | `PLAYER` | `GOALKEEPER` (המפתח הוא גם מפתח זר לשחקן) | |
| **מאמנים ושופטים** | `COACH`, `REFEREE` | – | |
| **משחקים** | `MATCH` | `MATCHTEAM`, `MATCHSTADIUM`, `REFEREEAT`, `PLAYERMATCHSTATS`, `GKMATCHSTATS` | |

בכל פאנל: חיפוש חופשי (גם על שמות של מפתחות זרים), דפדוף, **הוספה** (המזהה מוקצה אוטומטית ומוצג "יוקצה אוטומטית"), **עדכון לפי מפתח**, **מחיקה לפי מפתח**, ועריכה/מחיקה מהירה משורה. בפאנל פירוט, שדה ההורה (למשל המשחק) ממולא ונעול מראש.

## 5. מיפוי הדרישות למסכים

| דרישה בהוראות | איפה מתקיים |
|---|---|
| מסך כניסה שממנו נכנסים לכל המסכים | מסך הכניסה → סוחר (6 מסכים) / מנהל (8 מסכים) |
| CRUD לכל הטבלאות | 22/22 טבלאות: 7 של הבורסה + 15 של הליגה (סעיף 4.3), כולל `USERS` גם מצד הסוחר |
| השפעת פעולות, פונקציות ופרוצדורות על הטבלאות | קנייה/מכירה → `TRANSACTIONS`, `USER_SQUADS`, `USERS`; סגירת מחזור → `PLAYERS`, `PRICE_HISTORY`; שינוי מחיר ידני → טריגר → `PRICE_HISTORY` |
| הפעלת שאילתות שלב ב' (לפחות 2) | מסך "תובנות שוק": כל 8 השאילתות |
| הפעלת תתי-תוכניות שלב ד' (לפחות 2) | 4/4: `prc_execute_trade` (פרופיל שחקן), `prc_process_round_price_update` (מחזורים), `fn_calculate_portfolio_value` (סגל, חשבון), `fn_get_user_transactions` (היסטוריה) |
| עדכון: המשתמש ממלא מפתח והמערכת מביאה את השאר | "עדכון לפי מפתח" בכל פאנל (סעיף 3.3) |
| לא לראות ID אלא שמות דרך מפתחות זרים | `LEFT JOIN` אוטומטי לכל FK + בוחר לפי שם בטפסים (סעיף 3.2) |
| תצוגה ידידותית ויפה | ערכת העיצוב של שלב א' (כהה, ירוק-אמרלד), RTL מלא, הודעות הצלחה/שגיאה בעברית |

## 6. הוראות הפעלה

ראו את הקובץ [הוראות הפעלה.md](<הוראות הפעלה.md>). בקצרה:

```bash
docker compose -p fantasy up -d db     # PostgreSQL בקונטיינר PostgreSQL_DB
npm install
npm run db:restore                     # שחזור backup4.sql + Views לתוך fantasy_db
npm run dev                            # Vite (5173) + Express API (5001)
```

ואז http://localhost:5173.
